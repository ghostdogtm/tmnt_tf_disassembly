# Teenage Mutant Ninja Turtles: Tournament Fighters (NES, U) — дизасемблювання

[English version](README.md)

Сирці ca65, які збираються байт у байт у
`Teenage Mutant Ninja Turtles - Tournament Fighters (U) [!].nes` (Konami, 1993; mapper 4 / MMC3, 128 КБ PRG,
128 КБ CHR). Сирці в `src/` **згенеровані**: імена, коментарі, константи й формати даних беруться з трьох файлів
міток, які редагуються вручну (`tools/labels/`). `tools/disasm.py` пише сирці й звіряє результат з оригінальним ROM.

ROM у проєкті немає. Покладіть свій дамп (і CDL, що йде з проєктом) у корінь проєкту.

## Швидкий старт

Потрібні `ca65` / `ld65` (використано cc65 V2.19) і Python 3 (використано 3.13; `tools/frames_png.py` ще потребує
Pillow) у PATH. У корені проєкту мають лежати:

| файл | |
|---|---|
| `Teenage Mutant Ninja Turtles - Tournament Fighters (U) [!].nes` | **ваш власний** дамп гри (не в репозиторії, див. нижче) |
| `Teenage Mutant Ninja Turtles - Tournament Fighters (U) [!].cdl` | журнал коду й даних гри з Mesen 2 (є в git) |

**ROM немає в репозиторії, графіки теж.** Покладіть свій дамп у корінь проєкту з іменем, наведеним вище. Очікується:
262 160 байтів (16-байтовий заголовок iNES + 128 КБ PRG + 128 КБ CHR), CRC32 `AC05464F`, SHA-1
`182f901142530a509a7c9f5831b5a7f7f4c923a8`. Перевірити:

```powershell
python tools/check_rom.py
```

`tools/disasm.py` спершу робить ту саму перевірку і зупиняється з повідомленням, якщо файлу немає або це інший дамп.
Графіка CHR (`src/chr/`, `gfx/`) вирізається з вашого ROM під час збірки, тож комітити її не потрібно.

```powershell
python tools/disasm.py --build
```

Команда генерує `src/`, `config.cfg`, `assemble.bat` і `compare.bat`, розкладає CHR ROM у `src/chr/`, збирає
`game.nes` і друкує `build: IDENTICAL`, коли результат збігається з оригіналом. Після свіжого checkout її треба
запустити один раз: `src/chr/` у git немає.

Далі сирці можна збирати без генератора:

| | Windows | make (Linux, macOS, Windows з make) |
|---|---|---|
| зібрати `game.nes` | `.\assemble.bat` | `make` |
| зібрати й порівняти з оригіналом | `.\compare.bat` | `make check` |
| усі перевірки | — | `make test` |
| перегенерувати `src/` з файлів міток | `python tools/disasm.py --build` | `make gen` |

У Windows шляхи беріть у лапки: у назві теки можуть бути `!` і пробіли. Якщо інструмент не може надрукувати символ
у консолі, задайте `PYTHONIOENCODING=utf-8`.

## Як це працює

`tools/disasm.py`:

1. Читає ROM і всі CDL (CDL гри та `tools/mesen/cdl/*.cdl`, формат Mesen 2 `CDLv2` або FCEUX) і позначає кожен
   байт PRG як код, операнд або дані.
2. Трасує код, який CDL пропустив, від відомого коду й від рядків `entry` (у коментарях рядка позначка `T`),
   іде таблицями переходів після `JSR JumpTable` (D032, рядки `dispatch`), знаходить таблиці `.word`, таблиці з
   трюком RTS і пари таблиць lo/hi.
3. Визначає банк кожного операнда `$8000-$BFFF` (див. [банки](#залізо-й-банки)), дає імена цілям
   (`sub_`/`loc_`/`dat_`, якщо мітки користувача немає), посилання всередині підпрограми робить локальними `@мітками`.
4. Декодує відомі формати даних (текст, екрани, метаспрайти, скрипти ударів) і підставляє константи.
5. Пише сирці й `game.mlb` (мітки для Mesen), збирає ROM і порівнює з оригіналом.

Кожен рядок сирців має коментар із прапорцями CDL, зміщенням у файлі, `банк:адресою` і байтами:

```
  LDA objJumpVelX,X               ;C-J- 04777 02:8767: BD A0 04
```

Прапорці: `C` код, `D` дані, `J` ціль переходу, `S` вхід підпрограми, `T` знайдено трасуванням (не в CDL);
`-` немає. Байти, яких жоден CDL не бачив прочитаними, позначено `unread`.

Цикл роботи завжди однаковий: **правка `tools/labels/*.txt` → `python tools/disasm.py --build` → `IDENTICAL`**.
`src/` вручну не редагуйте: наступний запуск його перезапише.

## Файли міток

Повний синтаксис описано в docstring функцій `load_rom_labels` і `load_consts` у `tools/disasm.py`. Адреси
пишуться як `BB:AAAA` (банк : адреса CPU) у перемиканих банках 00-0D і просто `AAAA` у фіксованих ($C000-$FFFF).
`(?)` у коментарі означає неперевірене припущення.

**ram.txt**: `ADDR name [SIZE] ; коментар`. Якщо SIZE > 1, `ADDR+n` пишеться як `name+n`.

**rom.txt**: `LOC name ; коментар` і директиви:

| директива | значення |
|---|---|
| `code` / `data` / `words` / `rtswords RANGE` | примусова класифікація (rtswords: збережена адреса = ціль − 1) |
| `table RANGE N` | таблиця даних, N байтів у рядку |
| `numwords` / `dbyt RANGE` | 16-бітні числа, little / big endian, не адреси |
| `split LOC LOC N` | таблиці адрес lo / hi |
| `imm LOC LOC` | безпосередні операнди двох інструкцій — `#<ціль` / `#>ціль` |
| `ref LOC Name±N` | операнд інструкції за LOC пишеться як `Name±N` (перевіряється) |
| `alias RANGE RAM[/N] name` | у цьому діапазоні коду байти RAM мають інше ім'я |
| `bitskip LOC` | `BIT abs` ($2C), яким перестрибують наступну 2-байтову інструкцію |
| `entry LOC` | код, для якого не знайдено виклику: трасувати звідси |
| `dispatch LOC` | підпрограма знімає адресу повернення і переходить за вбудованою таблицею `.word` після `JSR` |
| `bank LOC TT`, `bankcall LOC TT`, `rawsym AAAA name` | підказки банків (нижче) |
| `text`, `charmap`, `screens`, `screentext`, `metasprites`, `movescripts`, `aiscripts`, `sound`, `soundptrs`, `framenames` | формати даних (див. [документи](#формати-даних)) |
| `note LOC ; текст` | рядок коментаря перед LOC |
| `module LOC name` | новий файл сирців з LOC |

**const.txt**:

| рядок | значення |
|---|---|
| `NAME = EXPR [@var ...]` | константа. `@var` прив'язує її до змінної RAM: вона замінює безпосередній операнд скрізь, де це значення записують у змінну, читають з неї або порівнюють з нею |
| `use LOC [LOC ...] EXPR` | безпосередній операнд цих інструкцій — EXPR |
| `data LOC EXPR, ...` | байти даних записуються виразами |
| `enum` … `endenum` | анонімний `.enum` |
| `struct Name field[:size] ...`, `array var Name` | `.struct` для масивів записів у RAM |

Кожен вираз звіряється зі справжнім байтом, тож помилкове ім'я ламає збірку, а не дає хибні сирці.

## Залізо й банки

- **PRG**: 16 банків по 8 КБ, MMC3 у режимі PRG 0. Гра завжди вмикає перемикані банки парами (R6 = n,
  R7 = n + 1, n парне), тож кожен банк має одну адресу CPU: парні банки 00-0C на $8000, непарні 01-0D на $A000,
  банк 0E на $C000 і 0F на $E000 (фіксовані). Кожен парний банк починається з власного номера; гра читає `$8000`,
  щоб дізнатися, яку пару ввімкнено (`rawsym 8000 BankIdAt8000`).
- **Стек банків**: далекі виклики кладуть поточну пару в `bankStack` (`$3D`/`$3E`), вмикають іншу й потім
  повертають попередню (F5DF-F5F3, окремий вхід для кожної пари; рядки `bankcall`). Звук працює в парі 00/01
  (`MapSoundBank` F669).
- Операнд `$8000-$BFFF` у перемиканих банках стосується пари, в якій лежить сам код. У фіксованих банках потрібна
  підказка: `bankcall` (код після `JSR` на підпрограму, що вмикає банк), рядки `bank` у rom.txt або згенерований
  `tools/labels/banks.txt` (пара, яку Mesen бачив під час виконання цієї інструкції). Без підказки операнд лишився б
  числом; таких не лишилося (`docs/coverage.txt`: unresolved 0).
- Код переходить межу парного й непарного банку всередині пари (наприклад, `JSR` на 0A:9FFF), тому генератор
  обробляє пару як одне ціле на 16 КБ.
- **CHR**: 128 КБ, перемикається банками по 1 КБ / 2 КБ; копії R0-R5 — у `chrBanks` ($32-$37).
- **IRQ**: скан-лінійне переривання MMC3 (F85E) ділить екран; `SetIrqSplit` (F814) вибирає обробник і рядок.
- Вектори: NMI F219, RESET F174, IRQ F85E.

## Що відомо про гру

Коротка карта; подробиці — у файлах міток (шукайте імена) і в `docs/`.

- **Режими гри**: `gameMode` ($20) розгалужує `RunGameMode` (F380, таблиця на F389): `MODE_TITLE`, `MODE_DEMO`,
  `MODE_GAME` (вибір бійця й бої), `MODE_KONAMI`, `MODE_LEGAL`, `MODE_OPTION`, `MODE_INTRO`, `MODE_ENDING` (?). Під
  час бою `modeSubState` проходить завантаження арени, підготовку раунду, вступ, бій, кінець раунду, паузу після
  нокауту, кінець матчу.
- **Головне меню** (`gameType` $2C): story, VS player, VS CPU, tournament, option. Налаштування: складність ($0125),
  швидкість гри ($0126, turbo скорочує удари й стрибки), таймер ($0127).
- **Об'єкти**: 16 слотів, масиви полів за адресами `$0400 + $10 × поле` (`objFrame`, `objY`, `objX`, швидкості,
  `objState`, `objPhase`, `objTimer`, `objBox`, `objPower` …). Слоти 0/1 — бійці, 2-5 — їхні атакувальні об'єкти,
  6 — м'яч.
- **Бійці**: `objSpriteSet` = персонаж (`CHAR_*`: Leo, Raph, Mike, Don, Casey, Hothead, Shredder), `objState` =
  `FST_*` (стоїть, стрибок, удар отримано, присід, спецприйом, захоплення …), здоров'я у `fighterHp` ($0590,
  $B0 = повне).
- **Джойстик**: `joyPressed` / `joyHeld` ($8E / $91, `BTN_*`). Боєць-комп'ютер грає, записуючи ці змінні для свого
  джойстика (ШІ комп'ютера в банку 0A і на EC5B-EF60, [docs/ai.md](docs/ai.md)).
- **Звук** (драйвер у банках 00/01, `SoundStart` 00:8E8D): id нижче `SND_MUSIC` ($2E) — ефекти (`SfxPtrs`),
  $2E-$46 — музика (`SongPtrs`, 4 канали), $47-$5A — семпли DPCM (`DpcmSamples`, по 5 байтів; голоси в банку 0E),
  $5B вимикає музику з затуханням. Потоки, канали й обвідні: [docs/sound.md](docs/sound.md).
- **Черга PPU** ($0300, виконує `RunPpuQueue` у NMI): команда, адреса; рядки, стовпці, заповнення й послідовності.

## Помилки гри

- **Друга перевірка відстані в Casey ніколи не відсіює** (ШІ комп'ютера, банк 0A, `0A:9619` і `0A:96B2`). `AbsDeltaBelow`
  починається з `TAY`, тож під час другого виклику `ObjDeltaY16` Y містить її межу ($50); підпрограма читає
  `objVelY[0] - objY,X` замість вертикальної відстані до цілі. Тому смуга «A лише при $30 <= |dy| < $50» ніколи не
  діє, і комп'ютерний Casey б'є A при кожному |dy| < $50. Перевірено точними значеннями в Mesen і з виправленим
  регістром (не з виправленою ROM): [docs/ai.md](docs/ai.md). Перегляд усіх викликів `AbsDeltaBelow` і інших підпрограм,
  що змінюють X/Y, другого випадку не знайшов; перегляд не йде за гілками.
- **Таблицю за персонажами читають за номером слота бійця** (`StartAttackIdleState`, `02:8352`). У `AttackIdleTimeByChar`
  по одному запису на персонажа, але код виконує `LDY objSpriteSet,X`, а далі `LDA table,X`, тож індекс — X (слот 0 або
  1): P1 завжди дістає 4, P2 завжди 3, решта п'ять записів не читається ніколи (у CDL вони лишаються непрочитаними).
  Підтверджено в Mesen: коли обидва бійці — Don (запис 3 = 4), слот 0 дістав 4, слот 1 — 3.
- **`GetBallRange` бере застаріле значення** (`EEB9`). Половина `|aiTargetDx|` будується в `tmp04`/`tmp04+1` лише коли
  `aiTargetDx` від'ємний; при `aiTargetDx >= 0` з відстанню до м'яча порівнюється те, що було там раніше. Mesen
  (забіг історії, 1 295 викликів): пара `tmp04` була $00/$02 у 990 з 1 007 викликів з `aiTargetDx >= 0`, хоча значення
  змінювалось; при від'ємному вона точно дорівнює `|aiTargetDx|`.
- **`AiTargetAttacksMe` читає не той байт для цілі зі слота 1** (`ED6B`). `LDA aiTargetDx,Y` використовує слот цілі як
  індекс у двобайтовому `aiTargetDx`, тож для AI слота 0 береться молодший байт і перевіряється його біт 7: вірно лише
  поки відстань менша за 128 пікселів. Знайдено читанням; Mesen показав 51 виклик з X = 0, Y = 1 у демо, але сама гілка
  рухомої цілі не досягалась.
- **`AiStepScript` перевіряє крок стрибка слота 0** (`0A:81C2`). У тесті «стрибок, близька дистанція: натиснути A» код робить
  `LDA objStep` без `,X`, тож для CPU-бійця на слоті 1 читає крок бійця 0. Mesen (прогін Story, 14 000 кадрів, 32 проходи
  гілки з A): тричі боєць 1 був у `FST_JUMP` зі своїм `objStep` = 2, коли в бійця 0 було 1, і CPU все одно натискав A;
  ШІ на слоті 0 цього не зачіпає.

- **`AiShredderNearHurtPick` індексує таблицю з 4 записів значенням 0-7** (`0A:9AE5`). У `AiShredderHurtActs` чотири
  записи, але код викликає `AiRandom8`, тож половина виборів читає байти після таблиці. Знайдено читанням; у Mesen не
  вимірювалось.

## Виправлення помилок (необов'язкові патчі)

Дизасемблювання завжди збирає оригінал, разом з помилками. Для кожної помилки вище є незалежний байтовий патч у
[tools/patches.py](tools/patches.py); [tools/patch_rom.py](tools/patch_rom.py) застосовує обрані до копії ROM
(джерело не змінюється, кожна правка спершу перевіряє оригінальні байти):

```
python tools/patch_rom.py --list                    # номери, назви, описи
python tools/patch_rom.py --all                     # game_fixed.nes з усіма патчами
python tools/patch_rom.py --only 1,3,ball-range     # обрані (номери або назви)
python tools/patch_rom.py --except 2                # усі, крім цих
make fixed PATCHES=all | 1,3 | -2,6                 # те саме через make (початковий - означає «усі, крім»)
```

| # | Назва | Помилка | Правка |
|---|-------|---------|--------|
| 1 | `casey-dy-gap` | друга перевірка відстані в Casey | два операнди JSR у банку 0A ведуть до заглушки з 7 байтів у `0F:EF61` (`JSR AbsDeltaBelow; LDY aiTarget,X; RTS`) |
| 2 | `attack-idle-time` | `AttackIdleTimeByChar` за слотом | `02:8352` `LDA table,X` -> `LDA table,Y` (1 байт) |
| 3 | `ball-range` | `GetBallRange`, застаріле значення | `0F:EEEE` стрибає до заглушки з 39 байтів у `0F:EF68`, яка заповнює `tmp04` для обох знаків |
| 4 | `target-attacks-me` | `AiTargetAttacksMe`, не той байт | `0F:ED6B` `LDA aiTargetDx,Y` -> `LDA aiTargetDx` (1 байт) |
| 5 | `step-script-objstep` | `AiStepScript`, крок слота 0 | `0A:81C2` `LDA objStep` -> `LDA objStep,X` (1 байт) |
| 6 | `shredder-hurt-acts` | таблиця з 4 записів, індекс 0-7 | `0A:9AE6` `JSR AiRandom8` -> `JSR AiRandom4` (1 байт) |

Заглушки лежать у невикористаному заповненні `$FF` у `0F:EF61-EF8F`, за фіксованими адресами, тож будь-яка комбінація
працює. Усі патчі разом застосовано до ROM і прогнано 12 000 кадрів бою історії в Mesen (заглушки 1 і 3 виконувались,
гра йшла далі); вплив на геймплей не вимірювався. Патчі зачіпають лише ШІ комп'ютера (патч 2 ще й час простою обох
гравців), більше нічого не змінюється.

## Інструменти для Mesen

`tools/mesen/` запускає Mesen 2 без вікна (`--testrunner` зі скриптом Lua), щоб записати, що гра виконує й читає.
Скрипти запускають власну копію Mesen проєкту (типово `./mesen`, не в git) на місці й правлять її `settings.json`
(Lua IO, обнулена RAM при вмиканні), тож не вказуйте їм Mesen, яким ви граєте. Запускайте лише один екземпляр за раз.

| інструмент | |
|---|---|
| `run_mesen.py` + `explore.lua` | бот, що проходить меню й грає (story, VS, налаштування, демо); записує виконані / прочитані байти, пари банків, записи в RAM, за бажанням знімки екрана; `--cfg` задає поля Lua (утримувані значення RAM, заданий наперед ввід) |
| `merge_runs.py` | зливає прогони в `tools/mesen/cdl/bot.cdl` і `tools/labels/banks.txt` |
| `new_code.py` | байти PRG, до яких дійшов прогін, але яких CDL ніколи не бачив |
| `montage.py` | аркуш мініатюр зі знімків екрана |
| `run_log.py`, `rom_read_log.lua`, `gen_sites.py`, `merge_logs.py` | журнал індексованих читань, перенесений з іншого проєкту (Mighty Final Fight); під цю структуру не адаптований (?) |

## Стан

- Збірка побайтово ідентична; lint, тест релокації й самотест проходять.
- Покриття (`docs/coverage.txt`): кожен байт PRG — код, дані або таблиця адрес, крім 36 000 байтів заповнення `$FF`
  (банки 07, 08, 09, 0B, 0D здебільшого порожні).
- Імена: близько 3 000 названих міток, 302 імен RAM, 1 194 констант; імен `sub_`/`loc_`/`ram_`/`dat_` не лишилось (кілька назв таблиць мають `(?)`, доки їх не перевірено в емуляторі). Потоки звуку (`Sfx<id>`, `Mus<id>_<канал>`, `Env<n>`, `_P<n>` для викликаних частин) і кадри метаспрайтів (`TurtleFrame<n>` … через `framenames`) генератор називає сам за їхніми таблицями. Гілки названі за змістом, де його видно з коду, решта за структурою
  (`...StepN` = запис таблиці переходів, `...Rts` = вихід RTS, `Goto...` = мітка лише з JMP); лишилось 1 967
  числових безпосередніх операндів (832 з них — просто 0 / 1 / $FF, решта здебільшого маски).
- Декодовані формати: текст, екрани, метаспрайти бійців і банки CHR, анімації, скрипти ударів, атакувальні
  об'єкти, спецприйоми, скрипти дій і дерева рішень ШІ комп'ютера, потоки музики й звукових ефектів, обвідні.
- Ще не декодовано: дія кількох звукових команд (`SC_SLIDE` і біти ехо прочитано з коду, на слух не перевірено; див.
  docs/sound.md) (банки CHR, палітри та знімок кожної арени є в docs/screens.md, розділ Arenas). Імена й припущення з позначкою `(?)` не перевірені.
